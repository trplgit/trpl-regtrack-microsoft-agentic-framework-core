The endpoint

This is the one Gaurav needs. Everything downstream is already built and running.

POST /api/insights/reports

Generates one report per requested dimension. Auth required — caller comes from the host's real validated principal, never the request body.

FieldTypeRequiredNotes
tenantIdintyesRe-validated server-side against the caller's eligible set — never trusted from the client alone.
reportTypestringyesfixed_holistic or dimension_selection
scopeobjectyes{"{"}"type":"tenant"{"}"} or {"{"}"type":"entity","entityId":92442{"}"}
periodstringyese.g. FY2025-26
requestedDimensionsstring[]only for dimension_selectione.g. ["Location","Entity","Act"] — at least one required for this report type
Picking several dimensions generates several independent reports — not one combined document. Each becomes its own background run, its own cooldown window, its own report. Picking "Entity" — alone or alongside others — always redirects that one dimension to a full fixed_holistic report; every other requested dimension is unaffected.

Fields, per report
FieldPresent whenNotes
dimensionalwaysThe dimension the caller actually picked — stays "Entity" even when reportType reads fixed_holistic. Use it to map a result back to a checkbox. null for a plain fixed_holistic request.
reportTypealwaysWhat actually runs, after the Entity redirect.

Supporting endpoints

Round out the flow — list tenants before generating, watch progress, open the finished report.

GET
/api/insights/tenants
Every tenant the caller is entitled to generate Insights for. Empty array is a valid 200, not an error.
GET
/api/insights/runs/{"{"}runId{"}"}/stream
Server-Sent Events. stage moves gathering → validating → composing → narrating → verifying → rendering → complete. Connection caps at 15 min; the run itself keeps going regardless — reconnect and resume.
GET
/api/insights/reports/{"{"}reportId{"}"}/content?tenantId={"{"}id{"}"}
Re-checks scope now, decrypts, mints a fresh short-lived read URL. Client renders it only in a sandboxed iframe — never innerHTML.

What Gaurav needs to do

The endpoint code is finished and tested. This is the integration, not a rebuild.

  1. Copy the source

    src/RegtrackInsights/Insights.Api/*.cs into the RegTrack API repo. Deliberately excluded from the worker's own build — these files were always meant to land here.

  2. Reference the domain library

    Everything those files depend on — request/response types, repository interfaces, the orchestration client — compiles into RegtrackInsights.dll. Project reference, built DLL, or an internal NuGet package, whichever matches how that repo already pulls in shared code.

  3. Implement the real caller

    IInsightsCaller is one property, int UserId. Map it from whatever authenticated principal that API already validates — same as every other endpoint there.

  4. Wire the registrations

    In that host's startup:

    builder.Services.AddInsightsData(builder.Configuration);
builder.Services.AddInsightsOrchestrationClient(builder.Configuration);
builder.Services.AddInsightsReportContentService(builder.Configuration);
builder.Services.AddScoped<IInsightsCaller, YourRealCaller>();

app.MapInsightsTenantEndpoints();
app.MapInsightsRunEndpoints();
app.MapInsightsReportContentEndpoints();
    Never call AddInsightsOrchestrationWorker (or the combined AddInsightsOrchestration) here. That starts a real dequeue loop — a second one would race the worker pod already processing the shared queue.
  5. Add the config keys

    ConnectionStrings:RegTrack, ConnectionStrings:DurableTaskHub, Azure:BlobConnectionString, Azure:BlobContainer, Reports:SasLifetimeMinutes, Reports:CooldownDays.
